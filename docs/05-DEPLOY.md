# Развёртывание, бэкап, восстановление (Этап 7)

> Статус проверки: команды `pg_dump`/`pg_restore`, миграции и приложение проверены на реальном PostgreSQL 18 и локальном запуске.
> **Сборка Docker-образа и `docker compose` в этой среде не запускались** (демон Docker был недоступен) — выполните первый деплой на стенде и пройдите чеклист ниже.

## Окружения
| | dev | test | prod |
|---|---|---|---|
| `APP_ENV` | `dev` | `test` | `prod` |
| БД | SQLite `otvet.db` | SQLite in-memory или PostgreSQL (`TEST_DATABASE_URL`) | PostgreSQL |
| Схема | `create_all` при старте | `create_all` | **только `alembic upgrade head`** |
| Секреты | значения по умолчанию | фиктивные | обязательны, приложение не стартует без них |

В `prod` приложение отказывается запускаться, если: `SECRET_KEY` короче 32 символов или по умолчанию, нет `ENCRYPTION_KEY`, БД — SQLite, `PUBLIC_BASE_URL` не https, включён `CRAWL_ALLOW_PRIVATE_HOSTS`.

## Первый запуск (VPS в РФ, Docker)
1. Установите Docker и Compose, откройте порты 80/443 (порт приложения 8000 слушает только `127.0.0.1`).
2. `cp .env.example .env`, заполните `SECRET_KEY`, `ENCRYPTION_KEY`, `POSTGRES_PASSWORD`, `PUBLIC_BASE_URL`. **Сохраните копию `ENCRYPTION_KEY` отдельно**: без неё токены Telegram/VK не расшифровать.
3. `docker compose build && docker compose run --rm app alembic upgrade head && docker compose up -d`
4. Создайте оператора: `docker compose run --rm app python -m app.cli create-admin you@example.com`
5. Поставьте перед приложением обратный прокси с TLS (пример Caddy ниже).
6. Проверьте: `curl https://otvet.example.ru/healthz` → `{"ok":true}`; зарегистрируйтесь, соберите базу, пройдите тестовый чат.

Пример `Caddyfile` (автоматический сертификат):
```
otvet.example.ru {
    encode zstd gzip
    request_body { max_size 4MB }
    reverse_proxy 127.0.0.1:8000
}
```

## Обновление и откат
- Обновление: `scripts/deploy.sh` — бэкап → сборка → миграции → перезапуск → проверка `/healthz`. При неудачной проверке образ откатывается автоматически.
- Ручной откат образа: `scripts/rollback.sh`.
- Откат схемы **не автоматический** (down-миграция может удалить данные): `docker compose run --rm app alembic downgrade -1` или восстановление бэкапа, сделанного перед деплоем.

## Бэкап и восстановление
- Ежедневный cron: `0 3 * * * cd /opt/otvet && scripts/backup.sh /var/backups/otvet` (хранит 14 копий, проверяет, что дамп читается).
- Копии храните вне сервера (другой хост/хранилище) и шифруйте на стороне хранилища.
- Восстановление: `scripts/restore.sh /var/backups/otvet/otvet-XXXX.dump` (остановит приложение, заменит данные, запустит снова).
- **Раз в квартал проводите учебное восстановление** на отдельной базе: дамп, который ни разу не восстанавливали, бэкапом считать нельзя.
- Сам процесс проверен: дамп → удаление данных → `pg_restore --clean` → данные и версия миграции на месте.

## Мониторинг и логи
- Контейнер пишет логи в stdout (`docker compose logs -f app`). В логах нет токенов и текстов сообщений клиентов; ошибки ботов пишутся с типом исключения.
- Healthcheck: `/healthz` (используется в `HEALTHCHECK` образа и в `deploy.sh`). Подключите внешний аптайм-монитор на этот адрес.
- Что смотреть: рост `refused`/`blocked` в отчёте, расход токенов в `/admin`, ошибки `worker iteration failed`, `telegram reply failed`, `vk reply failed`.
- Критичные ошибки (HTTP 500) логируются со стеком (`unhandled error`); подключите сбор логов/алерт по этой строке.

## Масштабирование (когда понадобится)
Один инстанс держит запланированную нагрузку. Дальше по порядку: Redis для лимитов (сейчас в памяти процесса), вынос воркера в отдельный контейнер (`Worker` из `app/services/worker.py`), pgvector/эмбеддинги для поиска, реплика PostgreSQL для отчётов.
